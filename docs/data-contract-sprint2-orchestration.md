# Data Contracts — Sprint 2 (Orchestration)
## AI-Powered Root Cause Investigation Platform

---

## 1. Purpose

This document defines the data contracts that **Team 2 (Orchestration)** depends on to build the Orchestrator agents.

It covers:
- The **`evidence_inventory` table** — a structured summary of all available evidence for an incident. The Orchestrator reads this to plan the investigation.
- The **`evidence_chunks` table** — the prepared, searchable evidence chunks that hypothesis agents retrieve via the RAG retrieval service.

> **Note:** Internal orchestration contracts (agent task assignments, agent results, final investigation output) are owned and defined by Team 2.

---

## 2. Representation Types

The following `representation_type` values are defined for **Sprint 2**. Team 1 populates chunks using these values and Team 2 filters on them when querying the RAG service.

> **Note:** This list is fixed for Sprint 2. It is intentionally designed to be extensible — new representation types can be added in future sprints without breaking existing contracts. Neither team should hardcode logic that breaks when an unknown type appears.

| Value | Source Evidence Type | Description |
| :--- | :--- | :--- |
| `log_cluster` | `application_log` | A compact cluster summary representing many similar log lines. |
| `metric_anomaly` | `metric` | A detected anomaly or changepoint in a metric time series with the anomalous period summarised. |
| `slack_summary` | `slack_message` | A concise summary of a relevant Slack incident thread preserving timeline, symptoms, and decisions. |
| `jira_summary` | `ticket` | A summary or direct chunk of a Jira ticket relevant to the incident. |
| `deployment_event` | `deployment` | A key deployment or configuration change event preserved with timeline context. |

## 3. Database Schema

### 3.1 Table: `evidence_inventory`

One row per incident. Generated by Team 1 after the Evidence Preparation pipeline completes. The Orchestrator reads this once at the start of an investigation to understand what evidence is available before planning which hypothesis agents to dispatch.

| Column Name | PostgreSQL Type | Nullable | Default / Constraints | Description |
| :--- | :--- | :--- | :--- | :--- |
| `inventory_id` | `UUID` | **No** | Primary Key (`gen_random_uuid()`) | Unique identifier for this inventory record. |
| `incident_id` | `UUID` | **No** | FK → `incidents.incident_id` `ON DELETE RESTRICT`, UNIQUE | Parent incident. One inventory per incident. |
| `total_evidence_items` | `INTEGER` | **No** | Check: `>= 0` | Total raw evidence records in `evidence_items` for this incident (before preprocessing). |
| `total_chunks` | `INTEGER` | **No** | Check: `>= 0` | Total RAG-ready chunks available for retrieval (after preprocessing). |
| `services_involved` | `JSONB` | **No** | Default: `'[]'::jsonb` | Distinct service names observed across all evidence. Example: `["order-service", "postgres"]`. |
| `time_range_start` | `TIMESTAMPTZ` | Yes | `NULL` | Earliest `event_time` observed across all evidence items. |
| `time_range_end` | `TIMESTAMPTZ` | Yes | `NULL` | Latest `event_time` observed across all evidence items. |
| `evidence_items_summary` | `JSONB` | **No** | Default: `'{}'::jsonb` | Count of raw records per `evidence_type`. See Section 3.1.1. |
| `chunks_summary` | `JSONB` | **No** | Default: `'{}'::jsonb` | Per-`representation_type` breakdown of chunk counts and services. See Section 3.1.2. |
| `generated_at` | `TIMESTAMPTZ` | **No** | `NOW()` | Timestamp when this inventory was generated or last regenerated. |

* **Index**: `idx_inventory_incident` on `(incident_id)`.

#### 3.1.1 `evidence_items_summary` JSONB Structure

Counts of raw evidence records per `evidence_type`. Tells the Orchestrator how much raw data was ingested before preprocessing.

```json
{
  "application_log": 1250,
  "metric":          480,
  "ticket":          4,
  "slack_message":   67,
  "deployment_log":  12,
  "generic":         3
}
```

Keys with zero records are omitted. The `generic` key may appear when the evidence normalizer cannot infer a specific type from the raw data — this is expected and should not be treated as an error.

#### 3.1.2 `chunks_summary` JSONB Structure

Counts of processed RAG-ready chunks per `representation_type`. Tells the Orchestrator what kinds of distilled evidence are available and which services they cover.

```json
{
  "log_cluster":      { "count": 15, "services": ["order-service", "postgres"] },
  "metric_anomaly":   { "count": 8,  "services": ["order-service"] },
  "slack_summary":    { "count": 3,  "services": [] },
  "jira_summary":     { "count": 2,  "services": [] },
  "deployment_event": { "count": 5,  "services": ["order-service"] }
}
```

Keys with zero chunks are omitted. Missing keys should be treated as `count: 0`.

### 3.2 Table: `evidence_chunks`

Stores the prepared, embedding-indexed evidence chunks produced by the Evidence Preparation pipeline. Team 2 accesses this table exclusively through the **RAG retrieval service** — no direct table access.

| Column Name | PostgreSQL Type | Nullable | Default / Constraints | Description |
| :--- | :--- | :--- | :--- | :--- |
| `chunk_id` | `UUID` | **No** | Primary Key (`gen_random_uuid()`) | Unique identifier for this chunk. |
| `incident_id` | `UUID` | **No** | FK → `incidents.incident_id` `ON DELETE RESTRICT` | Parent incident. |
| `content` | `TEXT` | **No** | None | Human-readable, retrieval-optimised text content of the chunk. This is what agents read and reason over. |
| `embedding` | `vector(1536)` | Yes | `NULL` | pgvector embedding used for semantic similarity search. |
| `representation_type` | `VARCHAR(30)` | **No** | Check: values from Section 2 | Category of preprocessed representation. |
| `evidence_type` | `VARCHAR(50)` | **No** | None | Original evidence classification (e.g., `application_log`, `metric`). Aligns with `evidence_items.evidence_type`. |
| `service` | `TEXT` | Yes | `NULL` | Service this chunk relates to. `NULL` for cross-service evidence (e.g., Slack, Jira). |
| `time_range_start` | `TIMESTAMPTZ` | Yes | `NULL` | Start of the time window this chunk covers. |
| `time_range_end` | `TIMESTAMPTZ` | Yes | `NULL` | End of the time window this chunk covers. |
| `source_evidence_ids` | `JSONB` | **No** | Default: `'[]'::jsonb` | List of original `evidence_items.evidence_id` UUIDs this chunk was derived from. For discrete sources (Jira, Slack, Deployment), contains all source IDs. For high-volume sources (log clusters), contains representative sample IDs (e.g. first, peak, last occurrence). |
| `metadata` | `JSONB` | **No** | `'{}'::jsonb` | Flexible extra fields that vary by `representation_type` (e.g., cluster size, anomaly score, ticket ID). |
| `created_at` | `TIMESTAMPTZ` | **No** | `NOW()` | When this chunk was created. |

* **Indexes**:
  * `idx_chunks_incident_type` on `(incident_id, representation_type)`.
  * `idx_chunks_service` on `(incident_id, service)`.
  * Vector index on `embedding` for approximate nearest-neighbour search (Team 1 to configure).

Source evidence references are stored directly on each chunk via `source_evidence_ids`. This enables zero-join, high-performance vector retrieval while preserving complete audit traceability back to the raw `evidence_items` table.

## 4. RAG Retrieval Service

Team 1 will deliver a **RAG retrieval service** that performs semantic search over `evidence_chunks` using pgvector. It accepts a natural language query with optional filters (representation types, services, time range) and returns a ranked list of the most relevant chunks with their content, metadata, similarity score, and original evidence references (`source_evidence_ids` for traceability back to `evidence_items`).

How Team 2 integrates this service into the LangGraph workflow is left to Team 2's design — for example, passing retrieved chunks through the LangGraph state, calling the service inside a node, or any other pattern that fits the orchestration architecture. Team 1's responsibility is only to deliver a working, callable service.

The exact interface will be agreed between Team 1 and Team 2 before implementation begins.

## 5. Team 1 Deliverables

The following is what Team 1 must deliver for Team 2 to start and complete their work.

| # | Deliverable | Description |
| :--- | :--- | :--- |
| 1 | **`evidence_inventory` table** | Populated with one row per incident after the Evidence Preparation pipeline runs. Schema as defined in Section 3.1. |
| 2 | **`evidence_chunks` table with embeddings** | Populated with processed, embedding-indexed chunks. Schema as defined in Section 3.2. Includes `source_evidence_ids` for zero-join traceability. `representation_type` values must match Section 2. |
| 3 | **RAG retrieval service** | A callable Python service that Team 2 nodes import and call directly inside LangGraph. Performs semantic search over `evidence_chunks` using pgvector. |
| 4 | **Inventory data available** | The `evidence_inventory` table populated and queryable for at least one seeded incident. How Team 2 reads and passes the inventory through the Orchestrator (e.g., via LangGraph state or direct query inside a node) is Team 2's decision. |

### Minimum viable delivery to unblock Team 2

Team 2 can build the Orchestrator structure and agent scaffolding immediately. To run end-to-end tests, Team 2 needs at minimum:

- **Item 3** (RAG retrieval service) working with realistic chunk data, even if backed by a small seed dataset.
- **Item 4** (inventory data available) returning a valid inventory for at least one incident.

If the full pipeline is not ready, Team 1 can provide **stub implementations** of the service functions that return hardcoded realistic data conforming to the schemas in this document.
